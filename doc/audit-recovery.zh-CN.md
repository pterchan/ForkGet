# 持久审计、升级与存储还原

[English](audit-recovery.md) · 简体中文

受保护的写入使用持久的尝试标识。SQL 在同一个原生事务中的操作共享一次尝试，包括使用保存点的操作。MongoDB 每条通过准入检查的写入命令使用一次尝试。审计日志保存可安全记录的标识、策略、计数和投递状态，不保存语句、参数、过滤条件、文档或原生错误消息。

SQL 在业务变更所在的原生事务中写入私有提交见证。逻辑目录、反射、差异、导出和回放均不包含该见证。原生事务提交前会重新校验分支和租约、策略以及实际生效的授权状态。该校验仅适用于当前提交。

代理会等待结果成功持久投递，再返回原生结果。如果已知原生操作成功，但无法确认结果是否投递成功，代理会保留该成功结果，并暂停接受新的受保护写入。后台任务只重试投递，业务 DML 不会再次执行。原生 COMMIT 确认丢失时，结果保持未知。当前文档内容无法证明过去某条 MongoDB 命令是否原子执行。

## 检查实际状态

```sh
forkget status --id 42
forkget audit --id 42
fg-control status --json
fg-control doctor
```

分支状态包含见证就绪情况、待投递结果、尚未查明的 SQL 结果、MongoDB 结果未知或部分生效的观察记录，以及阻止清理的事项。所有者只能查看自己的分支。运维人员查看的状态和诊断结果还包含部署的审计健康状况。请在控制服务和代理都可用时运行诊断命令。

`pending_delivery` 包含已获准且仍打开的事务。仅凭该字段无法判断写入是否暂停。`protected_writes_paused` 显示代理当前是否因投递受阻而暂停受保护写入。代理不可达时，该字段为 null。

## 协调升级协议

内部协议 **3** 要求控制服务与代理使用相匹配的二进制文件。不支持混用新旧版本进行滚动升级。仅重启控制服务时，旧代理仍会运行。请对元数据、服务后端数据，以及保留的捕获与结果存储进行一致性备份。

1. 停止接收新任务，并停止所有旧代理和控制服务。关闭应用连接池，确认旧的原生服务会话已全部退出。
2. 使用迁移账号运行 `fg-control migrate`，并应用更新后的[元数据运行时授权](../deploy/runtime-grants.sql)。保留已有校验和及已安装的迁移历史。
3. 启动新版本的两个服务之前，使用原生管理账号的配置和 `FG_BACKEND_DSN` 运行 `fg-control audit prepare`。该 DSN 必须指向同一个后端并使用同一个服务账号。准备步骤独立确认原生服务已无活动会话，无需启动代理。此步骤仅添加私有 SQL 见证存储及相应权限，并保留已有分支 ID 和业务表。
4. 启动彼此匹配的控制服务和代理。启动时同样会确认原生服务已无活动会话。见证准备失败的 SQL 分支仍可读取，受保护写入则会以 `reason=audit_storage_unprepared` 拒绝。
5. 重新开放应用连接池之前，检查诊断结果及分支状态。

服务账号仅获得见证的 INSERT 权限。垃圾回收账号获得 SELECT、DELETE 及必要的 PostgreSQL 模式使用权限。准备步骤校验对象标识、类型、键、约束和事务性存储是否完全符合要求，并拒绝触发器、外键、不记录日志的存储和不兼容的定义。若标记为就绪的见证缺失或与定义不符，常规准备流程不会自动重建。

MySQL 专用的分支管理员必须在现有写入命名空间内拥有适当范围的 TRIGGER 权限，以便查看触发器。服务账号和垃圾回收账号无需此权限。无查看权限的账号列出空的触发器列表时，无法据此证明没有触发器。回收见证时，会在管理员验证之前获取专用的原生锁，并持有该锁直至提交。收到原生 COMMIT 确认后，才在元数据中记录回收。参阅[服务后端角色](../deploy/README.zh-CN.md)。

出现新的写入尝试后，只能在升级后的版本上继续修复。请勿用旧二进制文件重新启动已经升级的部署。

## 核对孤立或结果未知的写入尝试

```sh
fg-control audit reconcile
fg-control audit reconcile --id 42 --drain
```

每轮核对都有处理上限。由当前代理正常运行的事务会继续执行。显式排空分支时，会关闭所选分支的会话并核对其待处理尝试。恢复时，先封存该尝试以阻止后续提交授权，并确认旧服务会话已退出，再检查可信的 SQL 存储。

- 找到匹配的事务见证即可证明已提交。
- 只有在已登记的关系、头部记录和标识均完好，且存储历史连续时，见证缺失才能证明已回滚。
- 存储不可达、缺失、不兼容或不可信时，结果保持未知，同时保留供日后恢复使用的证据。

经证实的结果会追加记录，原始的结果未知事件始终保留。尚未查明的结果和待投递结果会阻止物理清理与世代退役。已确认的见证分批回收，每批都有上限，并保留预留的存储头部记录。

## 独立还原、替换或时间点恢复

独立还原存储会破坏存储连续性。还原之前，停止应用访问、控制服务及代理。还原元数据或原生数据之后，务必**在启动新进程之前**将旧存储实例标记为失效。

```sh
fg-control audit invalidate-storage --id 42 --operator operator-name
```

代理离线时，该命令使用配置的服务账号证明旧原生服务会话已退出。命令会封存旧尝试，禁用受保护写入，并阻止系统根据旧的缺失证明错误地判定回滚。代理可用时，命令会先排空分支。原生存储发生变更后，必须按此流程将旧存储实例标识作废。

无法恢复证据时，运维人员可以显式确认保留未知结果。关闭应用连接池，并使用状态中报告的准确尝试 ID。

```sh
fg-control audit acknowledge-unknown --attempt <attempt-id> --operator operator-name
```

此操作会追加带有操作者身份的确认记录，并解除这一结果对清理的阻止。原结果保持未知，仍无法证明已提交、已回滚或 MongoDB 操作曾原子执行。旧结果已持久记录或得到显式确认后，可以替换已失效的见证存储。

```sh
fg-control audit prepare --replace-untrusted --id 42 --operator operator-name
```

执行替换前，必须已记录失效、相关会话已全部退出，且所有阻止恢复的事项均已解除。替换仅更改见证关系并登记新的存储实例标识，应用表保留原状。

## MongoDB 单机模式的边界

在首次可能向原生后端发送命令之前，先持久记录意图。多步骤捕获与回放会在元数据中以原子操作确认上一步的观察结果，并准备好下一次发送。最多只有一个实际执行步骤会保持未知。发送到原生后端之前，会拒绝 `w:0` 和不受支持的单向写入。

原生确认会保留原始响应。可安全记录的观察结果包括完整确认、带错误的确认、未发送或结果未知，还可包含计数和数字错误码。部分生效的操作会如实记录为部分生效。单机模式下的恢复无法根据当前 BSON 状态推断历史操作是否提交。

已持久记录为未知的结果会继续保持未知。旧服务会话全部退出且结果已持久投递后，该结果无需永久占用分支存储。延迟到达的原生确认可以追加一次与响应完全一致的观察记录，原始未知结果仍会保留。互相矛盾的延迟观察记录会被拒绝。回放隔离和验证规则仍然适用。
